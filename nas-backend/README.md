# HGhubX NAS 后端

把本地影片目录包装成 HGhubX 能直接接入的服务。零依赖，需要 Node ≥ 18 和 ffmpeg/ffprobe。

    node server.mjs /path/to/media --port 8080 [--cache ./cache] [--cache-max-gb 20]

## 随应用启动（推荐）
HGhubX 桌面端内置了对这个后端的托管：「设置 → 本机 NAS 服务」（或首屏的「把本机媒体目录作为片源」）里填好媒体目录并启用后，
应用每次启动都会自动拉起后端、把接入地址指向 `http://127.0.0.1:17680/`，应用退出（包括崩溃）时后端一并退出。
- 启动期间显示启动页：检查环境 → 启动服务 → 扫描媒体库 → 就绪；失败时给出原因（未装 Node / ffmpeg、目录未挂载、端口被占用等）并可重试或改用手动地址。
- 需要本机已装 Node.js ≥ 18 和 ffmpeg（`brew install node ffmpeg`）；后端脚本随应用打包，缓存放在应用数据目录的 `nas-cache`。
- 服务意外退出会自动重启（最多 3 次）；状态变化都会写进 `debug.log`（`[nas] …`）。
- 想单独运行（如放在真正的 NAS 上）则按下面的命令行方式使用。

## 自动分类
- 每个视频文件是一个条目，标题取文件名。
- 顶层文件夹名就是「分类」（客户端分类页动态展示），更深的子文件夹名是额外标签。
- 根目录下散放的视频归入「其他」。
- 封面：与视频同名的 `.jpg/.png/.webp`；没有就用 ffmpeg 截一帧，空闲时后台预生成并缓存。
- 以 `.` 开头的文件（如 AFP 留下的 `._xxx`）会被忽略。

## 客户端设置
「设置 → 接入地址」填 `http://<NAS-IP>:8080`。严格安全模式下，接入地址所在的内网主机会被自动放行。

## 播放与性能
两条播放路径，后端按文件自动选择：
- **直连（mp4/m4v/mov + H.264 + AAC/MP3）**：直接提供原文件，靠 HTTP Range 取流。零等待、不占缓存、快进快退随意跳。客户端本地代理用 1MB 对齐的块缓存（小请求 0 毫秒命中、缺块并发获取、顺序播放预读 8 块、拖动后首块只给 1MB 让画面更早出来），切到下一个视频前会预热它的开头和文件尾。
- **HLS（mkv/avi/HEVC/AC3 等）**：首次播放用 ffmpeg 封装（H.264+AAC 直接拷贝，其它才转码），缓存在 `cache/hls`。大文件边切边播（切出 3 段就返回），小文件（≤48MB）多等几秒直接给完整列表。

通用：
- 网络盘带宽是瓶颈：刚被请求、还没开播的 HLS 任务独占带宽，其余 ffmpeg 暂停（SIGSTOP）；退出时清理所有子进程；客户端中断请求时立刻停止读文件。
- 时长、编码信息持久化到 `cache/probe.json`，重启后不用再读网络盘；空闲时后台预生成时长和封面。
- HLS 缓存超过 `--cache-max-gb`（默认 20GB）后按最近使用时间淘汰。

## 字幕生成（日语 / 西班牙语等外语片）
播放页的 **CC 按钮**（快捷键 `V`）→ 选视频里说的语言 → 生成字幕。**全程在本机运行，音频和台词都不会发到外部服务。**

流程：ffmpeg 抽音频 → whisper.cpp 识别（`large-v3`，Metal 加速，带静音检测，识别 99 种语言）→ 按句拆分、过滤“幻听” → 本地大模型（Qwen2.5-7B）翻译成中文（没装则回退 NLLB）→ 缓存到 `cache/subs/`。
在 M2 上，一部 69 分钟的影片约 2 分钟完成；生成期间可以继续观看，完成后自动显示，并提示“字幕已生成”。

- **安装组件**（一次性，约 3GB）：`./setup-subtitles.sh`。装 whisper.cpp（brew）、识别模型 `large-v3-turbo`、静音检测模型、Python 环境与翻译模型 NLLB-200 1.3B，默认放在 `~/Library/Application Support/com.hghubx.app/nas-cache/models`（与应用托管的后端一致）。没装时 CC 按钮里会提示。
- **显示模式**：关闭 / 中文 / 原文 / 双语；`V` 循环切换，`[` `]` 调整字幕快慢（每次 0.5 秒）。
- **语言**：自动识别在开头是音乐或没人说话时可能判错，已知语言时建议直接选。非英语片里孤零零的 “Thank you” 等常见幻听会被过滤。
- 未安装翻译组件或语言暂不支持翻译时，只生成原文字幕。
- **日语识别准确度（实测）**：用 ReazonSpeech（日本电视节目真实对话，带背景音乐与音效，有人工标注）前 50 条、读音级字错误率（越低越好）：
  turbo 18.2% → large-v3 16.9% → **large-v3 + 调灵敏的静音检测 14.0%（当前采用）**。
  静音检测默认阈值 0.5 会漏掉带背景音的短台词，调成阈值 0.3、两侧补 200ms、最短人声 100ms（见 `subtitles.mjs` 的 `WHISPER_VAD_ARGS`）；再调灵敏到 0.2 反而变差。
  试过但没采用：关闭上下文（更差 17.7%）、音量动态归一化（更差 19.5%）、日语提示词（无差别）、放宽无语音阈值（无差别）。
- **翻译**：首选本地大模型 Qwen2.5-7B-Instruct（llama.cpp 的 `llama-server`，只监听 127.0.0.1，翻译完即退出；`translate-llm.mjs`）。每 15 条一批，并带上前面已译的 4 条作为上下文；漏译 / 原样抄回 / 夹英文单词的条目重问一次，仍不行再回退到 NLLB 补。
  NLLB 对口语短句很弱（实测“すごい”→“这太好了”、“ダメ!”→“没有!”、“はい”→“我可以”），7B 译成“真棒 / 不行！/ 好的”。7B 约 0.65 秒/条；3B 在“编号. 译文”格式下会直接复述日文，不可靠。
  7B 需要约 5GB 内存，8GB 机器上翻译期间会有明显的内存压力，播放可能略卡；不想用可以不装（`SKIP_LLM=1 ./setup-subtitles.sh`），会回退到 NLLB。
- **小声台词 / 呻吟 / 拟声词**：阈值 0.3 的静音检测对音量很小的台词和呻吟检测不到（实测一部 21 分钟的片子只出 0 条）。所以对白识别之后，再用阈值 0.1 的 `whisper-vad-speech-segments` 找出所有有人声的小段，扣掉对白已覆盖的，把相邻小段合并成 ≤12 秒的片段，**逐段单独识别**（`pendingRegions`），时间用小段在原片里的真实位置。整句都是呻吟类发声的（`isMoanText`），原文压缩成 `はぁはぁ…`，中文行直接给“啊…”，不交给翻译模型。
  同一部片：0 条 → 27 条，覆盖整部片，总耗时约 2.5 分钟；声音零碎的片子每个小段约多 4 秒。
  没采用：不开静音检测（whisper 会在安静处编出“次の動画でお会いしましょう”循环）；低阈值整段一起识别（被前面的“ああ”带偏，整段变成一条循环）。
  `kotoba-whisper-v2.0`（日语专用）逐条短音频识别很准（9.6%），但长音频会跳过内容，自己切块后整体并不比 large-v3 好（16.0%），而且要另外维护常驻服务，暂不采用。
  只装过旧版 turbo 模型的机器会自动回退到 turbo；可用环境变量 `WHISPER_MODEL` 指定模型文件名。
- 接口（GET + JSON，客户端经本地代理访问）：`/sub/capabilities`、`/sub/<id>/<ep>/status | start?lang=ja | cancel | remove | cues.json`。
- 可用 `--models-dir` 或环境变量 `MODELS_DIR` 指定组件目录。

## 注意
没有账号体系：登录接口接受任意用户名，点赞、收藏、评论只是占位。不要把端口暴露到公网。
